# بررسی بایت‌های شواهد بازیابی دادیار

این ابزار یک کنترل تکمیلی پس از تهیه manifest و امضای جداگانه اپراتور و بازبین است. چهار فایل واقعی را خارج از checkout می‌خواند و SHA-256 آن‌ها را با مقادیر داخل manifest مقایسه می‌کند:

- آرشیو بکاپ؛ سقف اندازه ۱ GiB
- فایل نشانگر بازیابی؛ سقف ۱ MiB
- گزارش Restore؛ سقف ۳۲ MiB
- خروجی آزمون اتصال دیتابیس؛ سقف ۱ MiB

نمونه اجرا:

node scripts/verify-restore-evidence-bundle.cjs --manifest /secure/restore.json --archive /secure/backup.archive --restored-marker /secure/restored-marker.txt --restore-log /secure/restore.log --database-probe /secure/database-probe.json

تمام مسیرها باید مطلق، canonical، خارج از Git checkout و فایل معمولی مستقل باشند. symlink، hard-link alias، FIFO، فایل تغییریافته حین خواندن، فایل تکراری و hash نامنطبق رد می‌شوند. آرشیو به‌صورت streaming hash می‌شود و در حافظه بارگذاری کامل نمی‌شود.

محدودیت مهم: نتیجه موفق فقط می‌گوید بایت‌های چهار فایل با hashهای manifest یکسان‌اند. این ابزار اصالت گزارش، صحت واقعی عملیات Restore، موفقیت معنایی آزمون دیتابیس، هویت واقعی امضاکنندگان یا مجوز انتشار را اثبات نمی‌کند. verifier امضا نیز تا زمان pin مستقل اثرانگشت کلیدها، هویت امضاکنندگان را تأییدشده اعلام نمی‌کند. نتیجه این ابزار هرگز deployment_authorized را true نمی‌کند.

فقط از داده ساختگی در آزمون‌ها استفاده می‌شود. آرشیو، لاگ خام، اطلاعات دیتابیس، کلید خصوصی یا داده موکل نباید وارد Git یا تیکت عمومی شوند.

## جداسازی مسیر شواهد

فایل manifest، آرشیو، گزارش Restore و خروجی probe دیتابیس باید بیرون از هر دو مسیر restore و Document Root تولید باشند. تنها فایل نشانگر بازیابی باید داخل restore root قرار بگیرد. این تفکیک مانع می‌شود که آرشیو یا گزارش، بخشی از درختی باشد که ادعا می‌شود از همان آرشیو بازیابی شده است.

نسخه فعلی همچنین مسیر manifest را در CLI از هر دو مسیر محافظت‌شده خارج نگه می‌دارد. نتیجه همچنان صرفاً تطبیق بایت‌هاست؛ موفقیت معنایی Restore و اتصال دیتابیس باید توسط اپراتور و بازبین مستقل بررسی و جداگانه امضا شود.


## مجوزهای فایل روی میزبان POSIX

برای جلوگیری از افشای آرشیو بکاپ، گزارش Restore، خروجی probe دیتابیس و manifest، verifier روی میزبان POSIX این چهار نوع فایل را فقط با مجوز مالک می‌پذیرد (برای نمونه `0600` یا `0400`). فایل نشانگر بازیابی می‌تواند برای سرویس وب Sandbox خواندنی باشد، اما نباید برای گروه یا سایر کاربران قابل‌نوشتن باشد. بیت‌های ویژه setuid، setgid و sticky برای فایل‌های شواهد رد می‌شوند. این کنترل، جایگزین جداسازی واقعی Sandbox یا تأیید انسانی نیست. آزمون‌های CI فقط فایل‌های موقت و ساختگی می‌سازند.


برای ساخت فایل‌های manifest، آرشیو، گزارش و probe، پیش از ایجاد آن‌ها `umask 077` را در همان نشست اپراتور اعمال کنید تا مجوز مالک‌محور از ابتدا برقرار باشد. فایل نشانگر را فقط در صورت نیاز سرویس وب Sandbox خواندنی کنید و هرگز مجوز نوشتن گروهی یا عمومی ندهید.

در `preview-release-preflight.cjs` تمام رکوردهای JSON شامل manifest، destination evidence، review attestation و trust store در POSIX باید متعلق به root یا کاربر سرویس و فقط در دسترس مالک باشند (معمولاً `0600` یا `0400`؛ بدون بیت ویژه). خواننده امضا نیز manifest را owner-only می‌خواهد و برای فایل‌های کلید عمومی و امضا، مالکیت root/کاربر سرویس و نبود بیت ویژه یا نوشتن گروهی/عمومی را کنترل می‌کند. در صورت رد مجوز، فایل را در پوشه امن خارج از checkout دوباره تولید کنید؛ مجوز verifier را سست نکنید.


## اجرای probe فقط‌خواندنی دیتابیس Sandbox

پس از Restore واقعی و ساخت دیتابیس/کاربر مستقل، خروجی اتصال را با ابزار زیر بسازید. این ابزار Restore انجام نمی‌دهد و فقط یک SELECT بی‌اثر اجرا می‌کند تا نام دیتابیس جاری، کاربر احراز‌شده، مقدار ۱ و نسخه سرور را بسنجد.

ابتدا فایل تنظیمات MySQL را خارج از Git checkout و با مجوز مالک‌محور 0600 بسازید. فایل باید فقط یک گروه [client] داشته باشد؛ دستورهای include و گزینه‌هایی مانند init-command رد می‌شوند. گذرواژه فقط داخل همان فایل محلی می‌ماند و به خط فرمان، گزارش یا Git منتقل نمی‌شود.

نمونه اجرا:

    umask 077
    node scripts/probe-isolated-database.cjs \
      --defaults-file /secure/staging-mysql.cnf \
      --expected-database STAGING_DATABASE \
      --expected-user STAGING_DATABASE_USER \
      --production-database PRODUCTION_DATABASE_NAME \
      --production-user PRODUCTION_DATABASE_USER \
      --restore-target-id IRANHOST_SANDBOX_ID \
      > /secure/database-probe.json

ابزار، فایل تنظیمات را با مجوز خصوصی به پوشه موقت 0700 کپی می‌کند، فقط فرمان mysql را بدون shell و با محیط محدود اجرا می‌کند و نسخه موقت فایل تنظیمات را حذف می‌کند. اگر نام دیتابیس یا کاربر متصل‌شده با مقادیر Sandbox تطبیق نکند، probe شکست می‌خورد. stderr خام کلاینت چاپ نمی‌شود تا اطلاعات اتصال افشا نشود.

خروجی باید دقیقاً از schema نسخه dadyar-isolated-db-probe-v1 پیروی کند. verifier بسته شواهد، کلیدهای JSON، شناسه Sandbox، نام دیتابیس و کاربر، نتیجه SELECT و زمان probe را بررسی می‌کند؛ زمان باید پس از تکمیل Restore و پیش از بازبینی مستقل باشد.

**مرز اثبات:** این probe فقط اتصال خواندنی به دیتابیس انتخاب‌شده و هویت دیتابیس/کاربر جاری را نشان می‌دهد. به‌تنهایی Restore را اثبات نمی‌کند، ثابت نمی‌کند دیتابیس تولید لمس نشده، هویت اشخاص را احراز نمی‌کند و مجوز انتشار نمی‌دهد. اپراتور و بازبین مستقل همچنان باید گزارش واقعی میزبان، جداسازی حساب، مسیرهای canonical و شواهد Restore را بررسی و امضا کنند. هرگونه دسترسی API، پیامک، ایمیل و وب‌هوک تولید در Sandbox باید خاموش بماند.
