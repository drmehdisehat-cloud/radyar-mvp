# درخواست ایجاد محیط بازیابی مستقل بکاپ دادیار

**وضعیت فعلی: انتشار مسدود است.** این درخواست صرفاً برای اثبات بازیابی در محیط جداگانه است و مجوز انتشار یا تغییر سایت اصلی نیست.

## متن آماده برای تیکت ایران‌هاست

لطفاً برای بکاپ وب‌سایت، یک محیط بازیابی موقت و کاملاً مستقل از حساب تولید فراهم کنید. اگر فایل، بکاپ کامل cPanel است، آن را با گزینه Full Restore روی همان حساب تولید بازیابی نکنید. ابتدا یک حساب میزبانی آزمایشی/جداگانه یا sandbox مستقل ایجاد کنید و Restore را فقط در آن انجام دهید.

الزامات محیط آزمایشی:

1. مسیر بازیابی و فایل آرشیو خارج از Document Root تولید و خارج از `public_html` سایت اصلی باشد.
2. دیتابیس و کاربر MySQL مستقل ایجاد شود؛ هیچ اتصال یا نام کاربری دیتابیس تولید در تنظیمات staging استفاده نشود.
3. DNS، فایل‌های موجود سایت، `main`، دیتابیس تولید، ایمیل‌ها و سایر سرویس‌های اصلی دست‌نخورده بمانند.
4. دسترسی عمومی و اتصال خروجی به درگاه‌ها، پیامک، ایمیل، وب‌هوک‌ها و APIهای تولید در محیط بازیابی غیرفعال باشد.
5. روش Restore و نسخه ابزار، زمان شروع/پایان، کد خروج، تعداد فایل‌های بازیابی‌شده و خلاصه خطاهای پالایش‌شده ثبت شود.
6. امکان خواندن یک فایل نشانگر مستقل مانند `dadyar-preview/index.html` و اجرای یک آزمون اتصال به دیتابیس آزمایشی فراهم شود.
7. مسیر واقعی و canonical محیط بازیابی و Document Root تولید، جداگانه اعلام و با `realpath` یا معادل معتبر سیستم ثبت شوند.
8. اگر پلن فعلی امکان Restore جداگانه ندارد، لطفاً به‌جای Restore درجا، حساب آزمایشی مستقل یا sandbox ارائه کنید.

لطفاً هیچ رمز، توکن، کلید خصوصی، اطلاعات موکل یا محتوای خام پایگاه داده را در تیکت عمومی یا مخزن Git قرار ندهید.

## شواهدی که مالک باید خارج از Git نگهداری کند

- شناسه و زمان ایجاد بکاپ، اندازه دقیق بایت و SHA-256 آرشیو دانلودشده.
- در Manifest امضاشده، `backup_provider: "iranhost"`، مبدأ دقیق `source_site_origin: "https://mehdisehat.ir"`، شناسه صادرشده توسط میزبان در `backup_id` و زمان UTC در `backup_created_at` ثبت شود.
- مقدار صحیح `archive_size_bytes` باید دقیقاً با تعداد بایت آرشیو دانلودشده برابر باشد؛ ابزار بررسی این تطبیق را انجام می‌دهد. شناسه بکاپ و زمان ایجاد باید در گزارش واقعی پنل میزبان قابل مشاهده و توسط بازبین تطبیق داده شوند.
- نوع بکاپ و روش/نسخه ابزار Restore، زمان اجرا و exit code.
- مسیر canonical محیط بازیابی و مسیر canonical Document Root تولید.
- نام دیتابیس و کاربر آزمایشی، متفاوت از تولید؛ بدون درج گذرواژه.
- تعداد فایل‌ها، SHA-256 فایل نشانگر بازیابی‌شده و گزارش پالایش‌شده آزمون اتصال دیتابیس.
- SHA-256 گزارش Restore و نتیجه آزمون دیتابیس.
- تأیید اپراتور و بازبین مستقل با دو امضای Ed25519 جداگانه و اثرانگشت کلیدهای عمومی که از کانالی مستقل و مورد اعتماد مالک pin شده باشند.

تا زمانی که عملیات Restore واقعاً در محیط مستقل اجرا و توسط بازبین مستقل بررسی نشده است، مقدار `restore_proven` باید `false` بماند. ساختن JSON، کپی آرشیو، تطبیق اندازه یا هش به‌تنهایی اثبات Restore نیست.

## پس از بازیابی مستقل

1. فایل منبع باید از commit بازبینی‌شده و با Git Blob SHA-1 همان commit pin شود.
2. نسخه مقصد موقت را خارج از Git checkout و خارج از Document Root تولید قرار دهید.
3. با دستور زیر فقط فایل staging را اعتبارسنجی کنید؛ این دستور فایل را کپی یا منتشر نمی‌کند:

```sh
node scripts/verify-preview-destination.cjs \
  /ABSOLUTE/TRUSTED-CHECKOUT/dadyar-preview/index.html \
  /ABSOLUTE/ISOLATED-STAGING/dadyar-preview/index.html \
  /ABSOLUTE/PRODUCTION-DOCUMENT-ROOT \
  EXPECTED_REVIEWED_GIT_BLOB_SHA1
```

4. پس از تأیید Restore، فایل مقصد، بازبینی انسانی احراز هویت‌شده، آزمون موبایل و صفر بودن درخواست‌های شبکه/API، بازبینی امنیتی و حقوقی و مجوز صریح مالک، مرحله انتشار عمومی جداگانه بررسی می‌شود.
5. مرحله عمومی فقط مجاز است یک پوشه جدید `dadyar-preview` و یک فایل `index.html` ایجاد کند. هیچ فایل موجودی جایگزین یا حذف نشود؛ `.htaccess`، redirect، symlink یا فایل دیگری اضافه نشود. هدرهای امنیتی لازم باید در سطح vhost/هاست تنظیم شوند.

**ممنوع:** Restore درجا روی حساب تولید، تغییر DNS، تغییر `main`، دستکاری دیتابیس تولید، فعال‌کردن API یا گفت‌وگوی هوشمند عمومی، و قرار دادن بکاپ یا اسرار در Git/گفتگو.
