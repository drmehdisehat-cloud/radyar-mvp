# اقدام مالک برای اثبات Restore مستقل دادیار

**این درخواست مجوز انتشار نیست.** هدف فقط اثبات بازیابی بکاپ و آماده‌سازی مقصد staging است. تا پایان کنترل‌ها، هیچ تغییری در `main`، DNS، فایل‌ها یا دیتابیس تولید مجاز نیست.

## متن آماده برای تیکت ایران‌هاست

لطفاً پیش از هر عملیات، درباره همین سرویس میزبانی `mehdisehat.ir` کتبی اعلام کنید:

1. کنترل‌پنل واقعی این حساب دقیقاً cPanel، SolidCP یا پنل دیگری است؟
2. فایل بکاپ موردنظر دقیقاً چه قالبی دارد، اندازه آن چند بایت است، شناسه بکاپ و زمان ایجاد آن چیست و کدام ابزار/نسخه برای Restore آن پشتیبانی می‌شود؟
3. آیا امکان Restore همین بکاپ در حساب موقت یا Sandbox مستقل وجود دارد؟ اگر پلن فعلی فقط Restore درجا دارد، لطفاً حساب آزمایشی جداگانه یا اجرای Restore توسط اپراتور میزبان را پیشنهاد کنید.
4. مسیر canonical محیط آزمایشی و Document Root تولید چیست و جداسازی فایل، دیتابیس و دسترسی شبکه چگونه تضمین می‌شود؟

تا دریافت پاسخ کتبی، هیچ دستور مخصوص cPanel یا SolidCP اجرا نشود. عنوان صفحه ورود عمومی، نوع پنل حساب واقعی را ثابت نمی‌کند. از گزینه Restore درجا روی حساب تولید استفاده نکنید.

پس از تأیید نوع پنل، لطفاً:

- بکاپ را فقط در Sandbox خارج از Document Root تولید و خارج از Git checkout بازیابی کنید.
- برای Sandbox دیتابیس و کاربر جدا بسازید؛ هیچ credential یا اتصال دیتابیس تولید در آن استفاده نشود.
- دسترسی عمومی و اتصال خروجی به ایمیل، پیامک، وب‌هوک، درگاه پرداخت و APIهای تولید را مسدود کنید.
- اگر Restore کامل شامل داده‌های تولید است، دسترسی آن را به اپراتور مجاز و مالک محدود کنید؛ داده‌ها نباید به مخزن، PR، Artifact یا تست منتقل شوند.
- گزارش زمان‌دار با timezone، شناسه بکاپ، قالب و اندازه دقیق بایت، SHA-256 آرشیو، ابزار/نسخه Restore، زمان شروع و پایان، exit code، تعداد فایل‌های بازیابی‌شده و خطاهای پالایش‌شده ارائه کنید.
- وجود یک sentinel بازیابی‌شده در restore root و نتیجه `SELECT 1` روی دیتابیس staging را ثبت کنید. fingerprint دیتابیس staging و production باید با SHA-256 شناسه‌های غیرمحرمانه محاسبه و متفاوت باشند؛ مقدار خام نام میزبان یا دیتابیس را منتشر نکنید.
- مقصد preview را در پوشه جدید `dadyar-preview` داخل staging بسازید. فایل مقصد باید فقط `index.html` و `INTEGRITY.json` باشد و هش SHA-256 هر دو فایل با Artifact همان Commit بازبینی‌شده تطبیق کند.
- مسیرهای staging، restore root، destination، Document Root تولید و Git checkout را با realpath بررسی کنید. مسیرهای دارای symlink، hard link یا هم‌پوشانی با تولید/checkout پذیرفته نیستند.

## شواهدی که باید خارج از Git نگهداری شوند

- شناسه، زمان، قالب، اندازه دقیق بایت و SHA-256 آرشیو واقعی؛
- زمان و exit code عملیات Restore و SHA-256 sentinel؛
- نتیجه `SELECT 1` و دو fingerprint متفاوت دیتابیس؛
- SHA-256 Artifact دانلودشده و SHA-256 فایل‌های مقصد؛
- مسیرهای canonical و نتیجه کنترل symlink/hard link؛
- گزارش پالایش‌شده و تأیید دو شخص مستقل از طریق کانال امن مالک.

برچسب `Complete`، اندازه ۱۴۰٫۳۸ مگابایت، وجود آرشیو یا تطبیق هش فایل بکاپ به‌تنهایی اثبات Restore نیست. Restore فقط وقتی قابل قبول است که در Sandbox مستقل واقعاً اجرا شده و sentinel، probe دیتابیس و مقصد بازخوانی شوند.

## محدودیت دسترسی و امنیت

اگر مالک نشست تعاملی کنترل‌پنل یا دسترسی محدود staging ندارد، اقدام لازم این است که خودش از داخل حساب احرازشده ایران‌هاست تیکت ثبت کند و از میزبان بخواهد Sandbox و دیتابیس مستقل ایجاد کند و Restore را انجام دهد؛ یا دسترسی محدود SSH/SFTP فقط به staging فراهم کند. دسترسی تولید لازم نیست.

**هیچ رمز عبور، OTP، توکن، کلید API، کلید خصوصی، اطلاعات اتصال دیتابیس یا داده واقعی موکل را در گفتگو، تیکت عمومی، Git، PR یا Artifact قرار ندهید.**

پس از جمع‌آوری شواهد، verifier موجود در `scripts/verify-preview-staging-evidence.cjs` باید در محیط مورد اعتماد اجرا شود. خروجی آن فقط تطبیق شواهد را گزارش می‌کند و به‌خودی‌خود هویت امضاکنندگان، صحت مستقل عملیات Restore یا مجوز انتشار را اثبات نمی‌کند.

حتی پس از موفقیت Restore، انتشار به HTTPS زنده staging، احراز هویت واقعی بازبین، بازبینی امنیتی و حقوقی، و مجوز جداگانه مالک برای همان Commit نیاز دارد. API و گفت‌وگوی هوشمند عمومی خاموش می‌مانند.
