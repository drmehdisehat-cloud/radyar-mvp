# آداپتور احراز هویت بازبین دادیار

## وضعیت

در شاخه آزمایشی، یک آداپتور JWT سازگار با الگوی OIDC و یک ترکیب‌کننده HTTP برای تحویل گزارش پس از بازبینی امضاشده اضافه شده است. این تغییر **به معنای انتخاب یا پیکربندی ارائه‌دهنده هویت واقعی نیست** و هیچ Listener یا مسیر عمومی را فعال نمی‌کند.

## قرارداد فنی

- فقط Bearer JWT با الگوریتم ثابت RS256 پذیرفته می‌شود.
- کلیدهای RSA عمومی با شناسه `kid` باید از قبل توسط مالک pin شوند؛ اندازه کلید ۲۰۴۸ تا ۸۱۹۲ بیت است.
- `iss` باید دقیقاً با صادرکننده HTTPS پیکربندی‌شده برابر باشد؛ `reviewIssuer` جداگانه به صادرکننده Trust Store بازبینی نگاشت می‌شود تا امضای بازبین و صادرکننده IdP با هم اشتباه نشوند.
- `aud` باید دقیقاً audience سرویس گزارش باشد.
- `sub`، `iat`، `exp` و `jti` الزامی‌اند؛ `jti` باید شناسه تصادفی base64url با طول ۲۲ تا ۱۲۸ نویسه باشد؛ `nbf` در صورت وجود بررسی می‌شود.
- عمر توکن حداکثر ۱۰ دقیقه است؛ انحراف ساعت حداکثر ۳۰ ثانیه.
- آرایه نقش‌ها باید دقیقاً شامل یک نقش `preview-reviewer` باشد و ادعای امضاشده `reviewer_independent` باید `true` باشد. نقش اضافه یا ادعای قدیمی `independent` جایگزین آن پذیرفته نیست.
- سرآیند Authorization تکراری، JSON دارای کلید تکراری، امضای نامعتبر، issuer/audience اشتباه و توکن منقضی رد می‌شوند.
- آداپتور در زمان ساخت به callback مورد اعتماد `isSessionActive` نیاز دارد و در هر درخواست، وضعیت نشست را با issuer، subject و jti تأییدشده از مخزن سمت سرور می‌پرسد. پاسخ فقط `true` پذیرفته می‌شود؛ نشست لغوشده، پاسخ `false`، خطا، قطعی یا timeout بین ۱۰ تا ۵۰۰۰ میلی‌ثانیه همگی با رد احراز هویت بسته می‌شوند. آداپتور خودش به شبکه یا مخزن ابطال متصل نمی‌شود؛ مالک باید callback واقعی را در محیط مستقل تزریق کند.
- پس از احراز هویت، امضای مستقل بازبینی Ed25519 همچنان باید به همان Commit، Git Blob و SHA-256 بسته متصل باشد. دفتر nonce از بازپخش جلوگیری می‌کند.

## محدودیت‌های عمدی

- هیچ OIDC discovery یا دریافت خودکار JWKS انجام نمی‌شود. کلید عمومی و `kid` از پیکربندی مالک تزریق می‌شوند؛ چرخش کلید دستی و کنترل‌شده است.
- این آداپتور به‌تنهایی هویت واقعی یا استقلال سازمانی شخص را اثبات نمی‌کند؛ فقط امضای توکنِ صادرشده توسط کلید pin‌شده و ادعاهای آن را بررسی می‌کند.
- `backend/configured-review-release-handler.cjs` فقط Handler می‌سازد؛ Listener، reverse proxy، HTTPS، گزارش‌خوان سروری یا اتصال به `backend/server.js` ایجاد نمی‌کند.
- این مسیر از API گفت‌وگوی هوشمند جداست و هیچ درخواست OpenAI ندارد.

## اقدام لازم مالک پیش از اتصال واقعی

۱. یک IdP مشخص و تحت کنترل سازمان انتخاب شود و audience اختصاصی برای دریافت گزارش تعریف گردد.

۲. نقش یکتای `preview-reviewer`، شناسه یکتای `jti` و ادعای `reviewer_independent=true` فقط برای بازبین مستقل و پس از کنترل مالک صادر شود.
۳. callback سمت سرور برای بررسی نشست/ابطال در هر درخواست، با timeout محدود و fail-closed، به مخزن بادوام و مورد اعتماد متصل شود.

۳. کلید عمومی RSA و `kid` از کانال امن به تنظیمات staging pin شوند؛ کلید خصوصی IdP هرگز به برنامه، مخزن یا گفتگو داده نشود.

۴. برای امضای اظهارنامه بازبینی، Trust Store جداگانه و کلید Ed25519 بازبین نگهداری شود.

۵. مسیر گزارش فقط پشت HTTPS و IdP واقعی نصب شود؛ دفتر replay و گزارش در مسیر خصوصی خارج از checkout و Document Root قرار گیرند.

۶. آزمون عملی با حساب بازبین واقعی، حساب فاقد نقش، توکن منقضی، replay و بررسی لاگ‌ها انجام شود. سپس بازبینی امنیت مستقل و مجوز صریح همان انتشار ثبت گردد.

آزمون‌های مخزن فقط از RSA/Ed25519، توکن، گزارش و هویت کاملاً ساختگی استفاده می‌کنند؛ هیچ داده موکل یا اعتبارنامه واقعی در آن‌ها وجود ندارد.
